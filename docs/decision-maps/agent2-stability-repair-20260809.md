## #2：先让监控反映真实情况

Blocked by: #0, #1
Type: Research

### Question

如何避免“用户收到失败回复，但后台显示全部成功、没有进模型”？

### Answer

第一批只改监控，不改用户可见行为：

- 在真实 Agent2 模型调用层记录模型调用次数、耗时和结果，不再从旧的 `llm_intent_seconds` 等字段猜测是否进模型。
- 在工具执行层汇总成功、无操作、需要澄清、阻断和失败回执；在最终回复形成后记录“用户可见结果”。
- 将“消息已消费”“业务操作成功”“回复已形成”“钉钉已受理”“最终送达”拆成不同状态，不能再统一写成 `processed`。
- 失败统计同时读取模型结果、工具回执和最终回复类型；“没有处理完整”和内部安全失败都必须进入失败计数。
- 监控写入失败不得阻塞用户回复，额外耗时目标小于5毫秒。

主要落点：`app/stream_runner.py`、Agent2工具运行时、Webhook事件状态及其审计记录。该批完成后观察一个完整工作日，形成后续批次的可信性能和失败基线。

## #3：让日报复制和最终答复只服从真实回执

Blocked by: #2
Type: Prototype

### Question

如何同时修复整篇复制失败、内部错误码暴露，以及“数据已经变了却回复失败”？

### Answer

按现有 `Operation Outcome`（操作结果）模型加深，而不是新建旁路：

- Agent2只表达“复制上一份日报”的语义和用户原始日期表达，不再提供数据库 `report_id` 或版本。
- 服务端解析日期后，按当前用户和来源日期唯一绑定来源日报，再读取可信版本；来源不存在或日期不清楚时返回结构化澄清事实。
- `copy_previous_to_today` 只接受服务端绑定结果，保持现有整篇复制业务规则及稳定条目结构。
- 同一用户目标中的依赖操作使用一个操作组：必须一起成功时在同一事务中提交；允许独立成功时，最终答复逐项说明已成功和未成功部分。
- 最终回复只读取已提交回执，禁止根据模型原计划宣称成功；技术错误码只留在审计中，Agent2收到的是可对用户说明的安全事实。

主要落点：`tool_calling/validation.py`、`production_daily_executor.py`、工具参数契约、`receipt_reply.py` 与操作结果汇总。验收至少覆盖：3种整篇复制说法、来源缺失、日期含糊、目标已有内容、重复执行、后续工具失败、未来条件请求不立即执行。

## #4：让晨报原因查询读取晨报事实

Blocked by: #2
Type: Research

### Question

机器人如何解释“我明明交了，晨报为什么说没交”，同时不猜原因？

### Answer

在Agent2统一语义主链增加只读的“晨报批次事实”能力，不增加问句关键词入口：

- 可信事实包括报告日期、晨报批次、生成时间、当时采用的日报快照、自动提交结果、收件人、每段发送状态、事故记录和事后修正记录。
- 本人只能查询自己的晨报归类和送达事实；团队负责人可查本团队；中心负责人按现有组织权限查看总体事实。
- Agent2先回答能够确认的事实。原因证据不足时明确说不能确认原因，并列出还缺哪类记录；不得用日报当前状态反推历史晨报原因。
- 查询始终只读，不修改日报、晨报状态或发送记录。

主要落点：新增一个深的晨报审计查询模块，接入既有 `knowledge_query`/类型化只读工具和统一答复流程；不在 `report_service.py` 增加晨报问句判断。

## #5：把休假表达、应交责任和晨报豁免分开

Blocked by: #4
Type: Grilling

### Question

用户在聊天里说“我休假”，机器人应该怎么处理，晨报是否自动免交？

### Answer

已确定两阶段方案：

- 立即修正：聊天中的休假表达可以被Agent2理解和回应，但不得自动改变日报应交责任，也不得承诺“未交不用担心”。Agent2先读取本人当日应交/豁免事实，再如实说明当前系统状态。
- 正式豁免：只接受可信来源，例如已批准的请假记录或被授权管理人员创建的日期化豁免记录；不能从闲聊、语音转写或个人记忆直接生成豁免。
- 晨报同时展示“应交、已交、未交、免交”，免交必须带来源和有效日期；过期自动失效。

现有晨报已经支持 `exemption_reason`，优先补齐可信来源和查询接口，不另建一套晨报。未接入可信请假源前，机器人只说明“已记录你提到休假，但当前是否免交仍以应交记录为准”。

## #6：长语音和引号内容必须保留原意

Blocked by: #2, #3
Type: Prototype

### Question

如何减少长语音、引号内原话被遗漏，又不写关键词规则？

### Answer

把“来源覆盖”纳入同一次Agent2语义结果：

- 每个准备写入的事项携带对应的用户原话片段；服务端只校验片段确实来自当前消息、所有工具参数可解析，不判断片段的业务含义。
- 对显式引号、分段语音和编号内容做通用结构完整性校验：被模型选择为来源的重要片段必须出现在写入事项或明确的澄清说明中。
- 模型无法确认长内容如何拆分时，先展示整理结果让用户确认，不静默删减；不能用程序自行拆分、合并或改写成“完成”。
- 写入后以实际日报快照回给Agent2组织答复，防止模型按原计划复述一个并未保存的版本。

该校验保护任何内容，不枚举“降薪、裁员”等词。验收覆盖中文/英文引号、无引号长语音、编号清单、同一句多栏目、用户要求保留原话和用户允许概括六类场景。

## #7：机器人取名必须有明确的当前消息依据

Blocked by: #2
Type: Prototype

### Question

如何保留王喜给机器人取名“兼爱”的能力，又不把“小绿，今天星期几”误当成取名？

### Answer

记忆能力仍由Agent2理解，但写入必须经过类型化依据门：

- 同一次Agent2语义结果明确区分“呼唤机器人”“询问机器人名字”“给机器人取名”“纠正机器人名字”和“设置用户称呼”。
- 只有“明确取名/纠正”可以生成 `assistant.preferred_name` 提案，并必须携带当前消息中的依据片段、角色和新名字。
- 服务端只校验依据片段存在、角色没有串用、来源是当前用户当前消息；不通过关键词自行决定用户意图。
- 不确定时自然追问，不写记忆；普通呼唤仍继续回答用户真正的问题。

王喜的“你叫兼爱，我叫王喜”必须继续通过；“小绿，帮我查日报”“谢谢小绿”“别人叫它小绿”等不得写记忆。

## #8：连续消息先合并，再按会话顺序执行

Blocked by: #2, #3
Type: Prototype

### Question

如何降低语音分片等待时间，又不重新出现消息乱序？

### Answer

将短时合并移到同会话执行锁之前：

- 同一用户、同一会话的片段先按到达时间进入短暂收集窗；收集窗封口后生成一个稳定批次。
- 批次封口后才取得同会话执行锁；一个批次内按原始顺序交给Agent2，后续批次仍严格排队。
- 跟随片段不重复执行、不重复发送；批次ID、成员消息ID和结果进入审计，便于逐条追溯。
- 单条普通消息不额外等待超过当前2秒收集窗；非同会话仍可并行。

验收包括2至5条快速文本、语音后短追问、前一批处理很慢、重复消息、跨会话并发和进程重启。目标是批次大小不再恒为1，快速片段排队时间显著低于当前46.5秒，同时保持完成顺序0次颠倒。

## #9：总体晨报分段必须可续发且不重复

Blocked by: #2, #4
Type: Prototype

### Question

总体晨报中间一段失败时，如何只补缺失段而不整份重发？

### Answer

为每个“报告日期+收件人+晨报批次”建立分段台账：

- 每段有稳定编号、正文校验值、发送状态、平台受理编号和最终送达状态。
- 发送器只领取尚未受理的段；核验器只核验已受理段；已最终送达段永不重发。
- 中间失败后保留已成功段，下次从第一段缺口继续；全部段最终送达后才标记整份晨报完成。
- 正文变化必须创建新批次，不能拿旧段编号覆盖新内容。

验收对每一个分段位置注入失败，并验证“只补缺失段、顺序正确、已送达不重复、不同收件人隔离”。仍坚持平台受理不等于最终送达。

## #10：未闭环查询默认不再倾倒全部历史

Blocked by: #2
Type: Grilling

### Question

用户不说时间范围时，如何兼顾“不漏旧事项”和“结果可读”？

### Answer

不静默隐藏旧事项，也不固定默认一个可能错误的时间窗：

- 用户明确说本周、上周、最近一周或全部历史时，Agent2按原意查询。
- 用户未给时间范围时，工具可以先统计全部可信候选；结果超过可读上限时返回数量和可选时间范围，由Agent2自然追问“看最近一个月还是全部历史”。
- 结果较少时可直接展示，但必须写明起止日期或“全部历史”口径。
- 历史测试记录依靠来源标记排除，不能通过“吃炸鸡、去游泳”等内容关键词过滤。

这样不会漏掉真正长期未闭环事项，也不会一次返回118项。现有“计划出现、后续工作未再明确提及；部门任一成员后续工作可闭环”的业务规则保持不变。

### Question

按什么顺序实施，才能把风险隔离在最小范围？

### Answer

按以下独立批次执行，不把所有改动一次性上线：

| 批次 | 内容 | 用户可见变化 | 发布观察点 |
| --- | --- | --- | --- |
| 0 | 固化线上源码并重建可追踪开发基线（#0） | 无 | 与当前线上逐文件一致、现行基线验证全部通过 |
